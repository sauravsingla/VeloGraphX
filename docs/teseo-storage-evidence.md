# Teseo same-algorithm storage evidence

This experiment isolates **storage/layout effects** by running the same VeloGraphX BFS implementation over VeloGraphX `DynamicGraph`, read-optimised `CsrGraph`, and an external Teseo adapter. The current workflow covers both `BasicIncrementalBFS<Graph>::recompute()` and real mixed insertion/deletion batches through `BasicIncrementalBFS<Graph>::apply()`.

The Teseo adapter is non-intrusive: the adapter graph does not expose VeloGraphX-style `vertex_count()`, `directed()`, `neighbors()`, `for_each_neighbor()`, or `apply()` members. It opts into the C++20 graph-access contract through ADL `vx_*` free functions. This demonstrates that a foreign mutable representation can be used without inheritance or modification of the foreign library.

## Contract

- Teseo repository: `cwida/teseo`
- pinned Teseo commit: `2c37c2831c4d2acaaa838a86e1318363ce68c45b`
- algorithm: identical `BasicIncrementalBFS` implementation for the mutable storage paths
- graph semantics: undirected simple graph, dense vertex IDs, unit-weight traversal
- source: vertex `0`
- recomputation repetitions: 5; medians are reported
- incremental sequence: 5 deterministic mixed batches containing an existing-edge deletion and a new-edge insertion
- timing: graph construction/loading excluded; recomputation and incremental apply/repair timings are reported separately
- correctness: complete BFS distance vectors must match across recomputation backends, then `DynamicGraph` and Teseo must match after every incremental batch
- runner: GitHub-hosted Ubuntu 22.04
- claim class: engineering evidence only, not a system-level Teseo performance claim

## Historical recomputation-only result

The earlier validated workflow covered only the storage-swap recomputation phase:

| Vertices | Edges | `DynamicGraph` | `CsrGraph` | Teseo adapter | Exact |
| ---: | ---: | ---: | ---: | ---: | :---: |
| 8,192 | 32,768 | 120.434 µs | 57.988 µs | 4,341.401 µs | yes |
| 32,768 | 131,072 | 500.383 µs | 234.284 µs | 21,854.866 µs | yes |

Those figures remain historical recomputation evidence only. They are **not a system-level claim that VeloGraphX is faster than Teseo**; they measure one fixed VeloGraphX BFS implementation through each storage interface. Teseo's native algorithms, tuning, concurrency, update throughput and other capabilities are outside that result.

The current workflow supersedes the architectural limitation of that earlier run by exercising Teseo mutation through `vx_apply_updates` and checking exact distances after every mixed update batch. New timing numbers should be cited only from a completed artifact generated by the current workflow.

## Mutation path

Before a Teseo write transaction, the adapter closes its read snapshot and iterator. `vx_apply_updates` then applies each requested insertion/deletion in a Teseo transaction, commits it, increments the adapter version, and allows `BasicIncrementalBFS::apply()` to continue through the same graph-access contract used by `DynamicGraph`.

The benchmark deliberately checks the **entire** distance vector after each batch rather than relying on a digest alone. This turns the external adapter into a correctness regression gate, not just a timing example.

## Reproduction

```bash
gh workflow run external-teseo-storage.yml --ref main
```

The workflow pins the external commit, builds Teseo from source, runs the VeloGraphX test suite first, executes both graph sizes, requires exact recomputation and incremental output equality, and records immutable experiment metadata. Hosted artifacts remain engineering evidence and must not be relabelled as publication-grade measurements.

A second independent mutable adapter based on Boost.Graph is also CI-gated so the graph-access contract is not validated against only one external library. A third adapter now pins and builds Sortledton commit `6eb638f3ad38f8a10a127e7e118528f4c8d07a6e`; its separate workflow requires exact recomputation and mixed-update incremental equality at 2,048 and 8,192 vertices. The workflow records its narrowly scoped constructor-validation compatibility patch and prohibits treating hosted timings as publication-grade system comparisons.
